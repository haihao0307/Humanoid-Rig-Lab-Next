## 实时预检停顿的继续修复

源码 `635486fe…` 的隔离普通页测试暴露了热矩阵没有代表的冷路径：20 秒双人手势与 30 秒混合动作均约 59.94 FPS、无超过 50 ms 的帧；但 60 秒真实 OBS 为 57.22 FPS，12 个超过 50 ms 的帧，最大 784.1 ms、人物 tick 最大 752.7 ms。`begin()` 的完整物理分析以及到站后按真实脚锚/物体姿态重新认证是主要同步停顿。正确的缓存必须因这些输入变化失效，不能放宽键或删检查来掩盖开销。

以上为分帧修正前的失败性能证据，归档前缀 `r6-cooperative-before-`；不是最终性能承诺。普通页没有保留测试网格、替换着色器或在测量中手动推进时间。冷浏览器两人体与头发生成就绪为 63.1–68.1 秒，也独立记录，不能由稳态 FPS 推断加载很快。

分帧版本将同一密集检查写成生成器；同步接口通过排空生成器保留兼容，NPC 队列提交则使用分帧入口。提交时仍先完整推演整串任务，全部通过后才写入执行计划；不能在后续步骤尚未检查时先执行前一步。`CharacterActivity` 把尚无 plan/skill 的预检也计为忙碌，防止队列误判完成或允许此时改体型。

`TaskAgent` 分别在 submission、transport、reach、lower、release 阶段预算约 3 ms 推进一批，记录实际最大批次时间、累计计算时间和总等待时间。等待保留最后安全姿态、脚锚、抓握与任务所有权；暂停、取消和替换终止旧迭代器。共享导航缓存只在一次 `.next()` 内安装，离开同步块即撤掉，不会暴露给另一个任务。物体姿态、尺寸、实际碰撞形状、摩擦/质量、目标范围和真实脚锚变化会失效；已经接近物体后的目标改变直接受控阻断，不把旧放置点当作新目标继续执行。

已持有物的短暂冻结复用原局部暂停机制，其他人物与自由物体继续运行。冻结或刚解冻的物体不能作为支撑证据，撤手认证后必须恢复物理步并重新确认落地支撑。人工等待不累计“抓握受阻”时间；恢复以后真实受阻与掌接触错误继续按原阈值报错。复核对象的微小刚体位姿变化时，用整个撤离路径最小净空减去变换位移上界，仍要求身体 8 mm、手骨 0.5 mm，未扩大容差。

新增回归：17 组任务生命周期；6 组完整多步/分支/失败位置的同步与分帧推演等价；11 组运输规划控制流；123 组原导航查询，加 8 组分步等价与 7 类无版本号几何变更；8 组 / 248 物理步的持物等待隔离；4 组 / 2,318 物理步的等待反馈。数值回归保持 1,254 个完整/投影候选无差异，48 组撤手仍通过。

第一版分帧普通页 `73e58c05…` 的 60 秒 OBS 达 59.69 FPS，原 734/784 ms 密集停顿已消除，实际批次最大 5 ms；仍出现 NPC 队列同步提交的 150/117 ms 尖峰。随后补齐整串提交分帧，并完成下述普通页实测与首跑截图。分帧改变检查完成时间，所以新的图集直接在第一次执行中采样阶段，不再以旧绝对时间重放的“0 差”作为验收条件。
