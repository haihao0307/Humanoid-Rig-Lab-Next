# R14 启动内存耗尽排查

2026-09-12。状态：Candidate。遵守仅文件验证要求，没有启动页面、人物模拟、Worker、曲面生成器、求解器或 GPU。

## 已知原因与证据边界

用户截图是 Chrome 整页崩溃，错误代码为 `Out of Memory`。这确认了内存分配失败；截图没有说明是系统可用内存、页面进程限制还是哪一次分配触发，也没有当前三角形数量或堆快照。

源码确认存在以下风险：

1. 原自适应细分只限制递归深度 20，没有整个人物的额外细分总量限制。二叉细分的一个种子三角形理论上可以产生 `2^20 = 1048576` 个叶三角形。
2. 原 canonical 顶点保护在 16777216 个才触发，主要用于边编号编码，而非合理的内存保护。全局位置、法线、掩码、父节点、空间索引、分割与边界记录会一直保留到各组生成完毕。R13 的图表内缓存上限不能限制这些全局集合。
3. 转换时先构造多组普通数字数组，再复制为 typed arrays；原索引、最终索引、重复面集合和后续分块会同时存活，形成峰值。空间索引桶还在每次插入时复制整桶。
4. 绑定需要邻接图、原始权重和双缓冲权重，因此过大的显示网格还会扩大后续内存需求。把计算移到 Worker 不能消除这些分配。

R12 的 120 秒总超时掩盖了持续增长的工作量；R13 取消总超时后，没有补充全局计算量和内存约束，是修复遗漏。以上是源码能确定的风险，不能据此冒充本次崩溃的逐函数内存测量。

## 本轮修改

- 默认 `interactive` 额外细分预算：身体 24000、左腿 8000、头面手足 40000、五官 16000、脚踝 2000，合计 90000。预算按图表分配，左腿径向图表单独保留份额；后续区域不会因为前面的曲面用尽全身预算而完全得不到细分机会。`balanced` 倍率 1.5，`close` 倍率 2，均有上限。
- 达到预算后接受当前较粗三角形，保留源曲面、原 trim、共享边拓扑和统一绑定。目标位置误差、边长或法线误差仍未满足时计入 `refinementLimitCount`；报告 `precisionLimited`，界面明确说明部分区域未达到目标精度。原系数包不变；显示细节会受预算影响。
- 全局元素保护：350000 顶点、600000 原始/最终三角形分别计数、250000 分割记录、700000 边界记录。超限在继续写入前抛出错误，由 Worker 失败路径清理，不让这些集合任意增长。该机制仍可能拒绝过大的模型；不是对所有设备都不会内存耗尽的承诺。
- 转换直接按实际唯一顶点数和索引数创建 typed arrays；finalize 和 materialize 消费后的索引解除引用；绑定之前释放 canonical 原始数组。空间桶使用原地追加，避免反复复制。
- 诊断保留全局顶点数、组内细分预算和受预算影响的三角形数。GPU 几何缓冲仍不等于进程总内存。
