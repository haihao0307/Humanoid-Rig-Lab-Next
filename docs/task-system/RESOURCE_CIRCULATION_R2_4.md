# 多人任务 R2.4：共享资源冲突改为主动机动

- 完整源码基线：`upload/human-workbench-20260915@2c10eda`
- 工作分支：`feature/human-task-workbench-adjustment-v2-fullbase`
- 前置能力：独立人物派单、预测绕行、同目标站位、四向交叉、狭窄通道主动循环
- 约束：资源冲突不得重新引入原地停车等待

## 本轮问题

旧逻辑只对持续任务做特殊处理：发现已有 NPC 正在搬运或推动时，将任务标记为 `resourceWait` 并留在原地。手动任务则仍可能在 `claimObject()` 阶段直接失败。

这会产生两个问题：人物可能长时间站住；同一物体、同一工位和全场物理操作三种冲突没有被区分。

## 本轮处理

资源冲突现在分成三类：

1. `object`：指定物体已经被其他人物预占、持有或操作。
2. `station`：目标工位已经由其他人物的操作任务占用。
3. `manipulation`：当前共享物理操作通道仍由另一人物使用。

发现冲突后：

1. 原任务重新放回该人物自己的队列首位。
2. 系统选择附近非冲突区域，或生成确定性的前后左右机动命令。
3. 人物实际执行一段行走任务，而不是进入停车计时器。
4. 机动结束后重新检查原资源。
5. 资源释放后继续原任务。
6. 连续多次仍没有机动空间时明确返回无解，不无限循环。

## 安全边界

当前物理世界虽然以 `objectId` 保存 manipulation，但多个完整人物同时搬运不同刚体还没有完成浏览器级稳定性与性能验收。因此本轮暂时保留“同一时刻一个物理搬运/推动操作”的保守限制，只把非所有者从停车改为主动机动。

这不是最终并发上限。后续只有在双物体并行搬运、共享物理回滚和八人物帧预算都通过后，才移除全局物理操作串行限制。

系统不会仅凭模板或名称相似就把用户指定的物体静默替换成另一件物体。自动替代必须等任务 schema 明确声明 `resourceGroup` 或允许替代，否则可能完成错误任务。

## 验收

`tools/test-npc-resource-circulation.mjs` 验证：

- 同一物体冲突被识别。
- 同一工位冲突被识别。
- 共享物理操作冲突被识别。
- 原任务保留在个人队列首位。
- 人物收到真实行走计划。
- 资源释放后原任务重新可执行。
- 状态中不存在 `waitS`，源码中不存在 `resourceWait`。

当前仍是源码与 Node 级验证；生成后的 `index.html`、浏览器视觉自然度和多人长时间运行需要集中装配后单独验收。
