- 工作分支：`feature/human-task-workbench-adjustment-v1`
- 基线提交：`ca3e659eb684435c3598170356016fec68db4c2f`

- 不在本轮直接修改：身体几何、步态生成、关节求解、面部、服装、最终总装页面

## 1. 当前源码事实

1. `body/NPCDefinitions.js` 当前只提供一个人物预览实例，能力声明为 `previewInstances:1`、`crowdRuntime:false`，界面也说明批量运行器尚未接入。
2. `world/ActivitySpace.js` 的活动空间快照明确声明 `multiResidentNavigation:false`。
3. `world/GridNavigation.js` 只把 `world.objects` 中的静态物体作为障碍；规划时不读取其他 NPC 的位置、速度、半径或预计轨迹。
4. `campGridPath()` 在任务开始时生成一次静态路线；目标站位被占用时直接抛出错误，没有目标候选站位、等待队列或资源预约。
5. `body/NaturalLocomotion.js` 沿既定 `route` 和 `routeIndex` 行走，不负责感知临时移动障碍、互相让行、动态改道或死锁恢复。

因此，当前问题不是简单的碰撞半径或速度参数错误，而是缺少真正的多人任务与交通运行层。即使上层复制出多个视觉人物，底层仍然会表现为多个单体控制器沿各自静态线路独立运动。

## 2. 需要纠正的方案假设

“每帧为每个 NPC 重新计算完整路线”不能作为主方案。这样会产生三个问题：

1. 大量 NPC 同时运行 A* 会快速增加 CPU 开销。
2. 多个角色根据同一瞬时画面反复改路，容易左右摆动和相互追逐式振荡。
3. 重新规划空间路线不能解决狭窄通道的先后顺序、同一工作位争用和多人抵达同一目标点的问题。

R1 采用分层交通系统：

- 低频或事件驱动的全局路线规划。
- 高频、短视距的局部避让。
- 狭窄位置和交互站位的预约。
- 无进展时的让行、后退、改道和等待恢复。

## 3. 任务派发模型

所有任务必须显式绑定人物实例，禁止继续依赖唯一的“当前人物”。

```js
{
  schema: 'jarvis/npc_task_assignment@1',
  taskId: 'task-...',
  targetNpcIds: ['npc-01'],
  dispatchMode: 'replace', // replace | append
  coordination: 'independent', // independent | cooperative
  priority: 50,
  command: '把红色训练箱搬到一区',
  createdAtMs: 0,
  failurePolicy: {
    maxReplans: 8,
    blockedWaitMs: 12000,
    keepTaskOnTemporaryBlock: true
  }
}
```

每个 NPC 保留独立状态：

- `selected`
- `taskQueue`
- `activeTask`
- `taskHistory`
- `navigation.goal`
- `navigation.route`
- `navigation.routeRevision`
- `navigation.status`
- `navigation.blockedBy`
- `navigation.reservationIds`
- `navigation.progressTimestamp`

同一条命令派给多个人物时，不允许简单复制完全相同的终点。系统先为每个人物分配不同的接近站位、等待位或协作位，再分别生成路线。

## 4. 人物选择与任务界面

任务工作台需要同时支持：

1. 在人物列表中逐个勾选。
2. 点击三维场景中的人物进行选择或取消选择。
3. 单选、多选、全选、反选和按职业筛选。
4. 清楚显示任务将发送给哪些人物。
5. `替换当前任务` 与 `追加到队列` 两种派发方式。
6. 单个人物暂停、继续、取消，以及选中人物批量操作。
7. 每个人物显示当前步骤、导航状态、阻塞原因、重规划次数和等待资源。

选中状态属于编辑器临时状态；正式任务派发、取消和优先级变化才进入任务历史。高频移动和局部避让不产生项目 revision。

## 5. 多人导航分层

### 5.1 静态导航层

保留现有网格 A* 的可用部分，但把静态障碍网格缓存起来，不在每个人物每次查询时重复构造全部障碍桶。

全局代价由以下部分组成：

- 距离代价。
- 静态障碍净空代价。
- 转弯代价。
- 当前拥堵代价。
- 已预约通道或交互位代价。

### 5.2 动态占用层

新增动态空间哈希，每次交通更新写入：

- NPC 实例 ID。
- 当前位置。
- 身体平面半径。
- 当前速度和朝向。
- 未来短时间预测位置。
- 优先级和让行状态。

邻居查询只检查附近桶，避免所有 NPC 两两比较。

### 5.3 局部避让层

局部控制器不改任务目标，只在下一小段时间内选择安全速度：

- 保持沿全局路线前进。
- 与静态物体保持净空。
- 预测邻近 NPC 的相对运动。
- 在允许速度和转向范围内选择碰撞风险最低的速度。
- 双方都在移动时采用对等避让；一方正在精确交互时由另一方承担主要避让。

局部避让建议以 10–20 Hz 更新，人物步态和画面仍可按渲染帧率运行。

### 5.4 站位和资源预约

物体、工作台、区域、门口和狭窄通道需要生成语义站位：

- `approach`：接近位。
- `interact`：交互位。
- `wait`：等待位。
- `exit`：离开位。

一个 NPC 获得交互位后，其他 NPC 选择其他候选位或进入等待队列。多人合作任务可以预约一组左右或前后协作位。

### 5.5 重规划触发条件

不按帧重跑全局 A*。出现以下事件时才重规划：

- 前方路线连续被动态对象阻断。
- 规定时间内沿路线的有效进度低于阈值。
- 目标移动或目标站位失效。
- 预约被撤销或等待超时。
- 人物被外力推出原路线走廊。
- 新静态障碍改变可达性。

每个人物设置重规划冷却时间，避免反复抖动。

## 6. 阻塞不再等于任务失败

导航状态机：

```text
PLANNED
  -> NAVIGATING
  -> YIELDING
  -> REPLANNING
  -> NAVIGATING
  -> WAITING_FOR_SLOT
  -> INTERACTING
  -> COMPLETED
```

只有以下情况才进入 `FAILED`：

- 静态地图确认不可达。
- 任务对象已经被删除且无法重新绑定。
- 输入任务本身无效。
- 超过明确配置的总等待期限。
- 用户主动取消。

普通碰撞预测、前方有人、通道暂时占用和目标位暂时被占用只能进入等待、让行或重规划，不得直接终止任务。

## 7. 死锁恢复

人物连续无进展时按固定顺序恢复：

1. 减速并短时等待，观察对方是否已经离开。
2. 根据优先级选出让行者，避免双方同时左右摇摆。
3. 让行者退到最近的安全侧位或后退位。
4. 释放非必要预约，重新选择局部通道。
5. 仍然阻塞时重新计算全局路线。
6. 狭窄通道采用通行令牌，保证一侧先通过。
7. 多次失败后进入可恢复等待状态，并在环境变化时再次尝试。

优先级不能只按任务优先级决定，还应包含：已经进入狭窄通道者优先、持重物者优先、正在精确交互者优先、等待更久者逐渐提升优先级。

## 8. 第一阶段容量边界

当前人物身体、IK、皮肤和步态比导航本身更可能成为性能瓶颈。不能因为导航支持大量代理，就宣称可同时运行大量完整 3A 人物。

R1 的客观验收规模：

- 桌面端：先验证 8 个完整活动 NPC，随后实测扩展到 16 个。
- 移动端：先验证 4–8 个完整活动 NPC。
- 更远人物采用更低的导航、姿势和表皮更新频率。
- 超过 16 个活动人物后，再评估 Worker、分区更新和视觉 LOD。

## 9. 必须通过的测试

1. 两人正面相遇：一方让行，双方任务均不终止。
2. 四人十字交叉：没有长期死锁，全部到达各自目标。
3. 八人前往同一区域：获得不同站位或有序等待，不重叠到同一点。
4. 目标位被占用：重新选择候选位，而不是立即失败。
5. 移动人物临时挡路：局部绕行或等待后继续原任务。
6. 狭窄通道双向进入：通行令牌产生稳定先后顺序。
7. 人物列表只勾选一个 NPC：任务不会泄漏给其他人物。
8. 多选追加任务：每个人物队列保持独立顺序。
9. 动态障碍移开后：等待任务能够自动恢复。
10. 固定随机种子下：交通决策和验收结果可复现。

## 10. 实现顺序

- 建立 NPC 实例注册表和任务/导航状态结构。

### P1：独立选人和派单

## 11. 多分支合并边界

任务分支优先新增和修改：

- `control/` 中的任务实例、派发和队列模块。
- `world/` 中的动态占用、预约和路线协调模块。
- 任务面板和任务测试。

任务分支不得改变动作关节求解、步态曲线和身体几何。需要动作线提供新的身体能力时，只增加版本化能力接口，不在任务分支重写动作实现。

`source/assembly.json`、`source/body.template.html` 和最终 `index.html` 属于高冲突文件。实现期间先把核心逻辑放在独立源文件，最后由集成提交一次性接入并统一构建。
