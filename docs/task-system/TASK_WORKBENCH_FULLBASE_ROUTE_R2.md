## 2. 仍然存在的三个实际问题

### 2.1 任务接收者存在双重语义

人口面板同时存在“人物勾选”和“任务对象：已选人物/全体人物”；主语义任务窗口又主要绑定当前人物。用户看到的人物选择、当前人物和最终任务接收者并非始终是同一个概念，容易发生勾选一人但任务仍发给全体，或主窗口只控制当前人物的情况。

### 2.2 动态交通只有等待，没有绕行和恢复规划

当前交通逻辑主要检查下一个路线目标是否被其他人物占用。连续扫掠在路段中间检测到人物时，底层仍可能进入 blocked/fault。目标持续被占用超过 30 秒时会抛出错误并阻断任务。系统尚未提供短距离侧移、局部绕行、重规划冷却和长期等待恢复。

### 2.3 同一目标、工作位和狭窄通道没有预约

多个人物仍可能前往同一目标点。工作位、接近位、等待位和通道先后顺序没有统一所有权，容易形成重叠、双向堵塞或反复互相等待。

## 3. 高效三阶段路线

### 阶段一：统一任务接收者

- 人物勾选集合成为多人任务的唯一接收者来源。
- “当前人物”只决定编辑与观察对象，不再暗中代表任务范围。
- 全体任务通过“全选”明确形成，不再保留容易误解的第二套范围状态。
- 主任务窗口逐步接入同一人物选择快照；派单结果逐人返回，不因一人拒绝而回滚其他已接收者。
- 保留现有 `NPCPopulation` 队列与 `Agent`，不另建平行调度内核。

验收：只勾选一人时只有该人收到任务；多选时每个人保持自己的队列、暂停与失败状态。

### 阶段二：交通等待升级为恢复式导航

- 路线段扫掠预测其他 NPC，而不只检查下一个航点。
- 短时阻挡先减速和保持支撑，再按确定性规则选择侧移或局部绕行。
- 原目标保持不变；临时绕行点完成后继续原路线。
- 只有静态不可达才失败；人物临时挡路进入等待、让行或重规划。
- 增加重规划冷却和次数记录，防止左右摇摆与每帧 A*。

验收：两人迎面和四人交叉不会因一次碰撞预测突然终止；阻挡移开后继续原任务。

### 阶段三：站位预约与死锁恢复

- 目标生成 `approach`、`interact`、`wait`、`exit` 候选位。
- 同一工作位只允许一个人物持有交互预约，其他人物使用不同接近位或等待位。
- 狭窄通道使用短时通行令牌。
- 无进展时依次执行等待、确定让行者、侧移/后退、释放非必要预约、重新规划。

验收：多人前往同一区域不会重叠在一个点；狭窄通道双向进入不会永久死锁。
