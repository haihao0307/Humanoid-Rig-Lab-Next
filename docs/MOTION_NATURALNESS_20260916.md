# 动作自然度：脚掌接管与平衡一致性

从统一 main `3c3e9a4b7b250f4c8db20c15e2e5fab4ca9ce568` 创建的 `fix/motion-contact-handoff-20260916` 分支继续推进第一阶段。用户要求“动作一定要自然，不要僵硬，开始按计划处理”，本次执行后台 CPU 动作回归与无头浏览器检查，不操作桌面鼠标。

## 本次改变

1. 起身后，旧实现只继承脚的位置，并使用 Agent 中近似的身体朝向作为脚朝向。现在从已提交骨架读取完整脚掌四元数及其相对绑定姿态的朝向。站姿衔接期间保持支撑脚的世界姿态；各自第一次真实摆脚时平滑释放俯仰、侧倾并对齐落脚朝向，落地后回到原步态机制。没有修改锁定 vendor。
2. 修正侧向负重的躯干补偿方向。身体右侧负重会向左补偿，左侧反之；原有幅度和时间响应上限不变。该模型仍是有界支撑代理，不是全身动力学或经标定的重心解算。
3. 精简预检骨架原先跳过平衡修正。现在完整骨架与预检都读取同一人物当前的平衡输入，避免浅拷贝保留失效的反馈对象；接触动作的肩膀投影与最终双手约束使用同一根位置规则。
4. 将平衡输入加入接触证书、搬运姿态和动作预检的失效条件。伸手终点的肩腕偏移也会随平衡输入更新，避免身体倾斜改变后仍使用旧终点。现有证书容量上限保持不变。
5. 保留此前动作失败时的相位、转身、平衡状态回滚修复，详见 `MOTION_EXECUTION_ROLLBACK_20260916.md`。
6. 真实浏览器进一步发现坐姿转起身准备时，脚掌被绕固定踝关节转平，脚趾进入地面，整体地面修正又破坏脚锚并导致拒绝。现在显式脚锚里的 q 也参与完整脚掌约束，准备阶段保留脚及脚趾骨架。补充 87 帧准备阶段的脚方向与全部足部后代位置验证；不扩大原有接触容差。
7. 保留脚掌后，浏览器又暴露了骨盆净空修正同样会抬离脚锚的问题。将地面修正提取到提交前的候选阶段：对没有手部约束的受控姿态，抬升身体后重算固定骨长的双腿、保持脚锚，再实际复查皮肤支撑采样。支撑小腿对骨盆抬升的响应可能很弱；仅在同一限制骨段且响应为正时使用局部斜率加速，每次加速修正最多 25 mm，总迭代上限 8。不能同时满足地面与接触时仍拒绝；后续骨长、脚位和关节门禁照常执行。CPU 测试新增有解骨盆净空、弱小腿响应收敛、无解脚底净空三类约束，文件检查跟踪新的调用顺序。该阶段增加皮肤支撑查询，群体 CPU 预算仍需实测。

使用已有采样与接触约束改善衔接，没有加入随机摇晃或修改原始动作采集数据。四元数插值采用现有工具；参考 [Three.js Quaternion](https://threejs.org/docs/pages/Quaternion.html) 的球面插值定义。

## 共享接口与兼容性

- 输入：任务模块仍给出目标、路线、交通约束。`resetFromPose({preservePoseContacts:true})` 读取已提交的人物脚掌世界姿态；新 `MotionLabPose.balanceInput()` 返回当前有效的 pitchRad、rollRad、pelvisLocal，未启用或支撑转换繁忙时返回 null。
- 输出：内核脚状态增加可选 `adoptedOrientation` 四元数，存在于原有内核快照中，首次摆脚落地后移除；无该字段的脚完全沿用现有朝向逻辑。预检和执行产生相同平衡输入下的候选骨架。预检不是未来所有动态负载的保证，逐帧提交门禁仍然保留。
- 兼容性：没有新增人物队列，没有改任务调度、外貌、面部或人物选择；NaturalLocomotion 的避让、预约释放、阻断恢复保持原逻辑。TaskAgent 的本次增量仅是动作预检输入失效条件；此前增量是动作回滚接口。未装配平衡扩展时，可选接口按 null 工作。
- 任务板块配合：正常调用路径不需要改动。不要在预检期间绕过动作接口修改骨架或反馈；若输入变化，沿用既有重试/拒绝机制。后续群体性能优化需要共同明确 desired velocity、实际速度、支撑状态和阻断原因的接口，不在本 PR 新建调度器。

## 已完成的 CPU 运行验证

- `test-motion-support-continuity.mjs`：18 个衔接采样，脚位误差约 1.1e-16 m，支撑脚四元数误差为零。两脚通过真实摆脚恢复，195 个 120 Hz 更新后收脚；最大相邻采样脚角差 0.01661 rad。该数值是回归测量，不等于自然度评分。
- `test-light-balance-feedback.mjs`：810 个行走采样，脚锚保持，补充左右镜像负重的反向补偿验证。
- `test-contact-preflight-equivalence.mjs`：两种体型，2,078 组完整/精简骨架比较，位置和四元数分量差为零。包含开启正负倾斜后的完整 205 点伸手路径、反馈对象替换、证书失效，以及同一次伸手中改变平衡后的世界手掌终点。
- `test-motion-execution-rollback.mjs`：三种回滚情形、18 步确定性重放。物理和可见提交是桩，步态、IK、反馈是真实生产代码。
- `test-standing-gait-height.mjs`：8 种体型、19,933 帧；16 次行走、16 次转身、8 次停止。另通过 phase、turn-command、walk-route、seated-preparation、motion-transition-range、standing-gesture-retarget 回归。
- 通过 npc-traffic-wait、npc-target-reservations、contact-preflight-jobs、release-motion。8 人预约用例只验证唯一站位；不代表八人同场渲染性能。释放回归共 48 情形、10,920 采样。

## 浏览器、文件与验收

新增 `tools/test-motion-runtime-browser.mjs` 使用本地真实生成入口、公开命令接口及完整动作/物理提交路径；只使用浏览器协议，不操作桌面鼠标。从重新构建的入口冷启动后，坐下、起身、前行 1 米、左转 90°、挥手均已各完成一次，并恢复可接续任务的状态。起身后脚掌接管的 140 个实际提交样本中，最大方向误差约 7.3e-8 rad；五项动作累计脚位误差约 1.14e-15 m。待六个人物均生成后，同场分发挥手，六人都各完成一次并恢复可接续状态；全程 pageErrors 为零。此用例没有统计动作重叠峰值或帧率，不能据此宣称六人满精度实时性能达标。

内部另从真实 WebGL 帧缓冲采样了站立、坐下中段、坐姿、起身准备、起身中段、再次站稳六个时点。已查看坐姿及起身各阶段：入口确实渲染真实人体，支撑动作可以完成；起身准备仍有较大的上肢外展与躯干侧倾，应作为后续上肢配合与重心时序的重点。静态采样不是连续动作自然度验收，不提交图片替代实现。测试较早阶段父页面仍显示对照人物生成覆盖层，因此父页面截图不计作动作外观证据。

用 `CHROME_BIN` 指定浏览器，`PLAYWRIGHT_MODULE` 可指定外部 Playwright 模块 URL，`MOTION_QA_DIR` 指定仓库外证据目录；默认地址为 `http://127.0.0.1:4173/index.html?qa=1`。显式设置 `HUMANLAB_SOFTWARE_GL=1` 可用软件 GL。软件渲染初次尝试发生截图超时；改用浏览器默认图形后继续检查。前几轮实际发现并修复了起身净空拒绝，上述五项通过结果来自重新启动的最终源码，不包括临时调试替换结果。

已通过 `node tools/build-pure.mjs`、`node tools/check-pure.mjs`、`python tools/audit-files.py`；不手改 index.html。交付前 GitHub API 再次核对 main 仍为 `3c3e9a4`，与本地基线一致，无新增提交需整合。CLI fetch 出现连接重置，远端基线核对使用 API 完成；没有合并其他板块或推送 main。

## 后续顺序与规模边界

先完成近景质量：起步预备、减速收脚、连续转弯、停走接续，逐帧测支撑脚滑移和根/躯干角速度，并从正侧面验收。随后加入受约束的步频、步幅、负重姿态差异，避免同场人物完全同相。所有变化必须服从任务目标与交通限速。

再做群体预算：测量 4/8 人整帧与动作 CPU 分位耗时、预检等待和丢失模拟时间；然后引入动作精度分级、远处降频、共享预算及空间邻域查询。16/32 人通过后才讨论更大规模。当前人口上限为 8，是编辑器保护值，没有百人能力证明；本次不提高它，也不修改任务板块的交叉通行调度。
