# 动作系统审评 R22

2026-09-12。审查对象为当前 Human-Workbench 的任务执行、Motion-Lab R2.2、姿态适配、肌力估算和物品物理连接。完成源码交叉核对、参数文件分析及公式推导；没有执行人物动作、浏览器或 GPU，也没有修改动作实现。以下角度与时间算例均不是画面实测。

结论：现有系统已经具备统一姿态提交、固定步长、脚锚、有限物品施力与失败恢复，但动作衔接和接触反馈存在具体接线缺陷。物品刚体动力学已经接入，人体仍由运动学轨迹驱动，尚未形成反作用力、身体平衡和支撑脚之间的反馈。因此，仅调整平滑参数无法覆盖这次发现的问题。

文中路径相对 `G:/Three.js/Human/Human-Workbench`，行号对应审查时源码。P1 表示应优先修复的功能正确性问题，P2 表示应随后处理的动作质量或建模问题。

## 优先发现

### 1. P1：下蹲发力读错骨盆高度

`body/StrengthBridge.js:37-38` 从 `agent.pos[1]` 计算蹲姿比例。但 `body/NaturalLocomotion.js:61-65` 把它设置为导航根；实际下蹲另由 `body/MotionLabActions.js:78-79` 降低姿态根。`body/MotionLabPose.js:30-31,145-147` 只提交真实骨架，不回写导航根。

因此 close、lift、lower、pushTravel 中，真实骨盆已下降，力量模块仍按接近站立评估。`body/StrengthModel.js:81-85` 的髋、膝、躯干需求、剩余手力与疲劳都会受影响。

建议读取本帧已提交的真实骨盆高度，并统一站立与低蹲参照。后续验收应对比同一物体在站立、半蹲、深蹲下的姿态输入与关节需求。

### 2. P1：直接坐下再起身，拼接了不同坐姿

`body/ReferenceMotion.js:75-78` 将 sitting→standing 直接接到 sitToStand。`tools/derive-motion-reference.py:183-186` 中，坐下结束为 CMU 113_08 第 350 帧，起身起点却为第 1400 帧。文件方向通道的接缝差：左上臂约 77.12°、右小腿约 63.54°。`control/BasicController.js:74-77` 仅用 0.25 秒混合。

这会要求人物快速切换手腿支撑姿势。建议选择与当前坐姿匹配的起身片段，或显式补上保持接触的坐姿转换；不能用延长混合代替缺失的支撑动作。

### 3. P2：抓握反馈只检查物体中心，漏掉旋转造成的脱掌

`world/PhysicsWorld.js:314-315` 的 gripErrorM 只表示中心位置误差。`control/TaskAgent.js:125-130` 虽计算真实物体到双掌的残差，却只记录统计，没有用逐掌位置和角度判定接触。

物品姿态控制有有限扭矩，转弯或侧撞时允许角度滞后。例如掌点离中心 0.3 m、物体旋转滞后 30°，掌点偏差可达约 15.5 cm，中心误差仍可为零。建议将真实逐掌残差纳入反馈，先降低目标速度或调整姿态，持续失效再阻断。

### 4. P2：抓紧与松开的指关节信号没有接入

`control/TaskAgent.js:162-179` 在抓取、搬运、释放时计算 curl，但最终 Human.pose 调用没有传它。`body/MotionLabPose.js:8-13,79` 仅将手及手指按固定源偏移整体旋转，没有独立屈指消费路径。

因此“闭合等待”发生了，指关节闭合没有发生。建议连接逐指屈曲、物体尺寸和抓放状态。另一个局部量 lean 也未传出，但接触参考本身包含躯干姿态，不能据此断言人物完全不前倾。

### 5. P2：伸手的手腕平滑，不能保证肘部连续

`control/TaskAgent.js:160-161` 只保存初始双掌。`body/MotionLabPose.js:74-75` 一进入接触 IK，就采用固定肘部参考方向，未继承当前肘平面。

以源骨架静态肩腕位置不变为条件，解析几何代入得到左右肘位置分别改变约 24.4、25.3 mm。这是源几何算例，当前人物实际跳动幅度待测。建议捕获初始肘平面，随伸手权重过渡，并在接近奇异姿态时保留上一有效平面。

### 6. P2：起身回站姿重设脚锚，混合时又清空接触误差

`control/BasicController.js:88` 调用 resetFromPose；`body/NaturalLocomotion.js:58` 重设为标准站距，没有继承实际脚位。随后 0.4 秒关节混合中，`body/MotionLabPose.js:93` 清空 errors。

两套脚位的差异可能由滑动消化，此时误差为零实际是没有约束样本。建议保留实际支撑脚锚；需要改变站距时安排换脚，同时继续计算混合过程的接触误差。

### 7. P2：连续行走仍然逐段停稳

`body/NaturalLocomotion.js:76-81` 要等最后路点的 command 清空且 isSettled 才返回结束。`control/TaskAgent.js:70,159` 的 walkHandoff 因而设置得太晚，上一段已经停步收脚。

例如“前走 1 米，再前走 1 米”不能保持连续前进。内部导航路点也按终点计算制动速度。建议区分经过点和最终停止点，提前提供后续路段切向与出口速度。

### 8. P2：换脚直接重设上体动作相位

`motion/vendor/full-body.mjs:60-63` 用当前摆腿重新赋值相位，双支撑期间不推进。当前来源踝高峰为左 .066667、右 .55；按默认 120 Hz、0.36 秒摆腿计算，换脚时跳过约 .075 或 .108333 周期，源上肢目标方向最大改变约 23.59°。

65 ms 一阶追踪会缓和位置变化，但没有保证速度连续，存在追赶与手脚不同步风险。建议维护连续展开的步态相位，以接触事件调整相位速度，并在过渡时保留速度信息。

### 9. P2：转身采用硬速度闸

`motion/vendor/controller.mjs:67-70` 将角速度直接限到 1.1 rad/s，支撑脚扭差超过 .28 rad 时又直接置零；脚目标朝向在起摆时确定。

默认站姿原地转 90°的公式推导中，第 31 tick 根部即停在约 .275 rad，第 51 tick 首脚才落下，中间存在至少约 0.175 秒的转动停顿。实际视觉强度未测。建议增加角速度与角加速度状态，并依据预计落脚朝向提前换脚和减速。

### 10. P2：加速度取模，把下降和水平制动都算成竖向增载

`body/StrengthBridge.js:33-38` 用速度差的模长估算加速度；`body/StrengthModel.js:66` 再把它统一加到重力负荷。

以纯下降加速度 2 m/s²为例，所需向上手力应为 m(g−2)，这里使用 m(g+2)，约高估 51%。水平制动也被加入竖向需求。建议保留加速度向量，先算物体所需合力，再结合实际力臂求关节需求。

### 11. P2：固定步长的渲染插值没有接上

`motion/vendor/clock.mjs:16` 返回剩余时间比例，但 `control/NPCPopulation.js:169` 没有传递它；`source/runtime.template.js:626-632` 推进后直接渲染最后一份姿态。

高于 120 Hz 或帧间隔不均匀时，会存在姿态重复或步进不均匀的显示风险。建议分离模拟姿态与显示姿态，用前后两个已提交状态插值，不回写物理。此结论不等于已经测得低帧率；GPU、GC 和主线程耗时仍需单独分析。

## 发力与自然度的能力边界

`world/PhysicsWorld.js:252-258` 中人体是 mass:0 的 KINEMATIC 球代理；`:218` 仅对物体施力。`control/TaskAgent.js:176-195` 先提交人体轨迹，再限制物品施力，反馈主要用于阻断。当前没有物体反作用力→人体关节/躯干→重心→足底支撑的反馈链。这是架构边界，应与上述接线错误分开评估。

低速和疲劳通过 `body/NaturalLocomotion.js:75,94` 缩慢整个动作时间实现，没有分别调节步长、步频与双支撑比例；存在全身慢放和脚长时间悬空的风险。受控足部在 `body/MotionLabPose.js:63-64` 只保留朝向，足跟、中足、脚趾随整脚旋转，尚无独立的足底滚动。实际自然度影响需要动作观察确认。

## 建议顺序与验收

先修力量姿态输入、真实抓握反馈、手指接线和不匹配的坐起片段；再统一步态相位、路点交接、转向与带接触约束的姿态转换；随后接入身体负重和平衡反馈，并补渲染插值。

后续动作验证应覆盖：连续两段行走、90°/180°转向、坐下后直接起身、伸手与抓放、轻重物体转弯、下降放置，以及不同显示帧率。记录脚锚漂移、逐掌位置/角度残差、关节速度与加速度、力量输入、施力输出和帧耗时。仅有骨长不变、目标可达、没有异常，无法证明流畅、自然或发力正确。

本轮没有进行上述人物运行验收，未将公式推导写成实测结果。审查期间另有并行工作，相关源码位置已再次读取核对；本报告只新增审评文档。
