# 动作破碎与卡顿的原因追溯

2026-09-13。用户要求追查前面逐步实现在哪一步出错。本轮只核对源码、版本记录、任务记录和已有运行证据，重新执行腕部连接数值回归；未继续修改运行源码，也未把旧截图当成本轮新实拍。

## 直接原因

### 1. 动作到蒙皮的适配层把两个不同关节的旋转混用

位置：`body/MotionLabPose.js`。修复前参考动作路径为 `rotations.set(radius,palm)`，手部接触 IK 路径也把手掌旋转直接赋给位于肘部的桡骨旋转节点。

前臂旋前/旋后绕肘腕轴旋转；腕部弯曲应围绕手腕。代码保留了正确的肘、腕位置，却让前臂蒙皮旋转后的末端离开腕关节。于是骨架线段长度正确、手掌位置正确，表皮仍会变成扁带并在手腕错开。

本轮重跑 `tools/test-motion-skin-attachment.mjs`：覆盖三档身高、多朝向、31 个挥手时刻及手部 IK，共 570 个双侧腕连接样本。重建旧旋转错误时最大端点偏差 0.254527 m；当前修正最大偏差约 5e-16 m。该故障可以独立数值复现，证据强于单凭截图猜测。

R9（2026-09-11）接入记录已描述这一姿态适配层、完整参考动作和原始验证规则。可以定位到该模块及接入阶段；由于 `MotionLabPose.js` 尚未进入 Git，不能把首次写入错误行精确归到某个提交。

### 2. 站立手势直接使用了完整录制动作的下半身

位置：`control/BasicController.js` → `body/ReferenceMotion.js` → `body/MotionLabPose.js`。

之前挥手直接使用通用 `r2ReferenceDescriptor`。姿态构建中有参考动作时默认不使用独立脚锚，因此录制者的骨盆变化、腿方向和脚旋转也被应用到当前人物。整体向上修正只能避免最低点穿地，不能同时约束两只脚落地。

这属于动作组合和重定向问题。之前仅修复“起始站姿膝角被录制范围误拒绝”，解决了动作无法启动，却没有解决动作启动后的支撑方式，更没有检查完整皮肤形变。

当前专用站立手势描述器保留起始骨盆和世界脚锚，录制上身继续驱动手臂。坐卧完整动作不因此改成站姿。

### 3. CPU 贴地查询超过了多人固定步的时间预算

位置：`CompactWorkbench.minimumSupportY` → `r2DeformTissuePoint` → `r2DeformPoint`，由姿态提交的地面净空检查调用。

修复前约 2165 个支撑样本/人，120 次模拟检查/秒，两人每秒约 52 万次样本变形。旧 DQS 内层反复通过数组加减乘、切片和叉积创建临时对象。后续肌腹与混合蒙皮增加了这一条 CPU 路径的计算量。

旧运行测得贴地查询约 4.7 ms/人/模拟步。两人仅这项就约 9.4 ms，已经超过 120 Hz 的每步 8.33 ms 预算，还没有算姿态、快照、共享物理和绘制。固定时钟继续补算积压步骤，进一步延迟显示。连续双人挥手实测约 7.35 FPS，主因有直接计时证据。

当前标量计算保持采样数、步频和算法，2000 组数值对照与旧向量公式最大差约 9e-16 m。修复后连续双人挥手约 59.44 FPS，最终混合动作 30 秒约 59.94 FPS。没有做逐次历史版本性能二分，不能精确分配每次早期改动各自增加了多少开销。

### 4. 肩腋折痕来自尚未验收的曲面与变形组合，不能归入已修的腕部错误

现有管线包含来源拟合曲面、肩腋参考形体抬升、肩部权重过渡、肌腹变形，以及肩胸区域的 LBS/DQS 混合。`ANATOMICAL_POSE_REPAIR_R3.md` 记录了 90 mm 的最大局部参考形体抬升和 80% LBS 混合，也明确记录仍有肩顶折角及局部非邻接三角交叉。

这些早期记录本身就表明整套肩腋结果未合格。局部映射的正行列式、连续权重、CPU/GPU 数值一致，都不等于最终组合后的表面自然且无自交。本轮未进行逐层关闭/恢复的对照，因此不能断言某一个形体系数单独造成了全部折痕，也不能把来源拟合称为已经证明无错的基底。

## 为什么之前没拦住

1. R9 的提交检查覆盖节点数量、单位旋转、固定骨长、肘膝范围及 IK 残差，没有检查蒙皮旋转后的前臂端点是否还连接到手腕。缺失的是必要的不变量。
2. 挥手完成条件主要是骨架方向跟随录制数据。错误若存在于关节旋转与皮肤的对应关系，任务仍可被判完成。
3. 后续任务验证集中在派发、轮数、暂停和恢复。远景截图与完成计数没有覆盖用户实际观察的近景形变。
4. 之前约 60 FPS 的报告来自短时巡逻/搬运观察段，未覆盖连续双人挥手的重负载。用这段结果回应整体流畅性会产生误导。
5. 肩腋已经记录未通过完整验收，后续仍继续接多人和长任务，缺少基础人体动作合格后再扩展的集成门槛。文档标注未验收不能替代实际修复，也不能卸除实现责任。
6. Git 只有 2026-09-09 和 2026-09-11 两个现有提交，多个关键新增模块仍未跟踪。可以确认直接代码原因与文档阶段，但缺少逐步、可独立重放的源码检查点。

本次结论不把用户提出的巡逻、长任务、多人、阴影要求当成错误原因。实现应当验证这些要求下的正确性和开销。基础缺陷被暴露后，需要先对同一人物、同一动作逐层确认曲面和蒙皮，而不是继续依靠增加示例来证明动作系统合格。
