# 人物母体的体型、外貌与 NPC 派生体系研究

## 研究结论

Human-Workbench 适合继续发展为“参数定义人物、函数生成身体、能力约束行为”的人物母体。优先路线是在现有 R2 函数曲面之上建立有界、可追溯的形体变化层，并让骨架、蒙皮、头发、接触点和动作适配共同读取同一份人物定义。

当前最缺的不是更多外观按钮，而是从语义参数到完整人物的生成链。现在的不同 NPC 主要体现为身份、任务、力量和生理配置不同，身体仍为同一个来源形体。要生成外貌不同的人，需要把“固定来源参考”与“由参考派生的个人形体”明确分开。

建议采用一个共享人物契约，分别推进身体、脸部、材料毛发、运动和性格行为。母体可以逐步包含多个有共同接口的人体原型；没有必要要求一个静态参考形体覆盖儿童、成年男女和极端风格化比例。第一阶段先完成当前成人参考附近的受限变化，验证生成链完整性，再扩大适用范围。

本文以 2026-09-12 本地文件内容为依据，覆盖 README 所述 R13 启动修正、R11 人物系统、R10 表皮连接与 R9 动作接入。以下分为源码事实、公开技术依据和设计建议。没有执行人物生成、页面、Worker、动作或 GPU，未评价当前实际画面；新增接口和参数均为研究提案，尚未实现。美术方向暂按兼容现有成人形体、可逐步扩展的方案处理。

## 一、当前项目的实际起点

| 环节 | 文件证据 | 对母体建设的影响 |
| --- | --- | --- |
| 体型入口 | `body/CharacterPresets.js:2` 的 `CHARACTER_MORPH_LIMITS` 为空；第 13–14 行固定身高与肤色 | 当前没有已接通的体型参数空间；修改输入 JSON 不会自动改变身材 |
| 随机派生 | 同文件第 18 行 `seededCharacterPreset` 修改种子、ID、名称 | 随机种子目前不能被当作外貌多样性的实现 |
| NPC 能力声明 | `body/NPCDefinitions.js:33` 声明 `morphs:[]`、`arbitraryStature:false`、`crowdRuntime:false` | 多个定义不等于多个不同身体，更不等于多人同时运行 |
| 几何身份 | 同文件第 37 行 `geometryKey()` 返回固定来源 SHA | 未来不同形体若继续共用此键，会无法区分派生几何 |
| DNA 导出 | `body/HumanDNA.js:13` 标记 `fixedReferenceShape:true`，第 16 行分离瞬时状态 | 已有配方、来源、状态分离基础，适合扩展而不必另建一套并行身份系统 |
| 曲面 | `reconstruction/assembly.mjs:15` 的生成入口没有人物形体参数 | 需要将人物定义传至曲面求值，现有质量选项只改变采样精度 |
| 骨架 | `body/ReconstructionRig.js` 直接从 `R2_RIG` 生成静态节点、骨长和接触偏移 | 改身材必须生成个人中立骨架，不能仅改变表皮 |
| 动作校验 | `body/MotionLabPose.js:7,101` 从固定 R2 节点读取参考与骨长 | 骨长变更后，姿态构建、插值和校验都必须切换到同一份个人参考 |
| 蒙皮与接缝 | R10 使用共享拓扑、接口绑定根、八权重 DQS | 必须保留跨分区的一致位置和权重，避免在新变形层重新制造接缝 |
| 头发 | `reconstruction/hair.mjs` 从头皮曲面域求发根，但同时读取固定头皮半径场 | 头型变化后，发根、方向和用于包络判断的半径场都要同步 |
| 材料 | `body/CompactWorkbench.js:181` 仍使用固定的分部颜色；眼睛着色也含常量 | 需要明确的材质参数入口，不能仅在角色定义中添加一个肤色字段 |
| 行为选择 | `language/NPCRoutineController.js:104–110` 根据疲劳、冷却和需求筛选配方 | 可以在已有调度中加入个人偏好，不必先替换整个任务系统 |

虽然上级目录叫 Three.js，当前主要人物渲染器实际在 `source/runtime.template.js:189` 获取原生 `webgl2` 上下文，`CompactWorkbench.js` 直接上传属性和双四元数调色板。因此 Three.js 的 `morphTargetInfluences` 不是本项目现成可调用的解决方案。它能作为常规技术参照，但新增形变必须接入现有函数求值和着色路径。

需要保留的资产是 R2 参考函数、同源语义节点、R10 共享边界与绑定关系、R11 暂存提交机制、Motion-Lab 固定步长与接触所有权，以及 HumanDNA 中的证据状态。来源形体只是一个静态解剖参考，不能据此宣称拥有真实人群分布、个体关节标定或动态软组织数据。

## 二、公开技术中值得借用的部分

| 路线 | 公开依据 | 适用判断 |
| --- | --- | --- |
| 统计参数人体 | SMPL 将身份形变、姿态相关形变、关节位置回归与蒙皮组合起来。[1] | 借鉴“形体变了，关节也跟着变”和“身份与动作修正分离”；当前单一 R2 来源不足以训练可信的人群统计模型 |
| 参数化脸部 | FLAME 分离头部形状、表情、关节运动及姿态修正。[2] | 借鉴脸型身份与表情的分层，不能用持续皱眉充当一个人的永久脸型 |
| 语义控制映射 | MetaHuman RigLogic 把有语义的控制通道映射为关节运动、局部形变和相关材质控制。[3] | 借鉴“用户参数 → 求解层 → 多系统结果”；其 DNA 保存几何和各级资源，与本项目函数资产政策不同 |
| 空间自由变形 | Sederberg 与 Parry 的 FFD 用空间变形作用于几何，可进行整体或局部变形。[4] | 与现有参数曲面更相容，适合生成阶段的大比例调整；需要另外设计解剖约束和边界条件 |
| 双四元数蒙皮 | Kavan 等的 DQS 减少传统线性蒙皮的塌陷问题；缩放和剪切需要额外处理。[5] | 保留现有 DQS 负责姿态。把个人身材写入新中立形体和绑定骨架，不直接向现有刚体调色板塞入非均匀缩放 |
| 层次行为组织 | StateTree 区分状态、进入条件、任务和转换。[6] | 借鉴职责与转换边界，在现有任务执行器上加入选择层；本项目不需要因此迁移到 Unreal |
| 最小人物描述 | 本项目锁定的 Object DNA 宪章强调身份、语义锚点、约束、配方、状态和证据。[7] | 人物定义保存可重建关系，生成几何临时存在；外貌与行为都通过版本化契约组织 |

综合判断：近期采用“语义参数 + 受约束空间变形 + 局部函数修正 + 个人骨架”最合适。直接替换成预制网格角色管线，会改变当前资产约束；直接用隐式神经网络生成完整人物，则会增加可控性、求值成本、绑定与来源追踪问题。二者都不是这轮最短的落地路径。

这里推荐的是架构方法，不是已经评测胜出的算法实现。SMPL、FLAME 的数据模型不直接进入交付；若未来引入特定模型版本，需要分别确认其数据、代码和输出使用条件。FLAME 官网已区分 2023 Open 与早期研究版，不能沿用“所有版本都只有研究许可”的旧说法。[2]

## 三、母体定义的分层

| 层 | 保存内容 | 变化频率 | 主责任 |
| --- | --- | --- | --- |
| 参考原型 | 来源曲面、参考骨架、语义域、基准坐标 | 按来源版本变化 | 提供可追溯基准 |
| 个人身体 | 身体比例、体积轮廓、脸型参数、个体锚点规则 | 创建或显式编辑时 | 决定“长什么样” |
| 外观程序 | 皮肤、眼睛、头发、局部特征与服饰配方 | 创建或装扮变化时 | 决定表面外观与附着 |
| 能力与表达习惯 | 力量配置、可达范围、动作风格上限 | 低频、显式更新 | 决定“能做什么、怎样表达” |
| 性格与经历 | 偏好、动机、社会关系、长期记忆摘要 | 低频更新 | 影响选择，不直接修改网格 |
| 运行状态 | 疲劳、当前任务、情绪、接触、姿态 | 随模拟推进 | 描述“此刻怎样” |

建议在现有 NPC definition 的 `character` 内扩展身体与外貌；将性格放入行为定义的版本化扩展；把证据、配方、坐标和生成版本继续放在 HumanDNA 外层。避免同时维护 NPC JSON 和另一个“真正的 DNA”而产生两份互不一致的人物真值。

下图是建议的依赖方向，方框代表职责而非必须新建的文件：

```text
来源 R2 + 个人定义 + 明确版本
                 │
          参数解析与约束求解
                 │
       ┌─────────┼─────────────┐
       ↓         ↓             ↓
  个人中立曲面  个人中立骨架   语义锚点与包络
       │         │             │
       └──→ 个人绑定 ←──────────┘
                 │
       皮肤 / 头发 / 附着物
                 │
  性格与需求 → 任务选择 → 能力预检 → 动作适配 → 最终姿态提交
                                 ↑
                     当前世界、接触和身体状态
```

“DNA”在这里是工程上的人物配方，不是遗传学模拟。性格与外貌默认独立采样；需要某种艺术角色组合时，通过明确的创作预设实现，不宣称从脸型、肤色或身体比例推断性格。

## 四、体型参数怎样设计

### 4.1 参数必须具有可检查的含义

不要把底层曲面系数、骨骼矩阵或顶点位移直接作为创作界面。对外给有意义的量，对内求出低维形变系数。每个参数记录单位、中立值、适用原型、允许域、耦合约束、影响部位、对缓存的影响及来源状态。

| 参数组 | 可表达的方向 | 实现注意 |
| --- | --- | --- |
| 骨架比例 | 身高、腿身比、肩部骨架宽、骨盆宽、臂长、颈长 | 分清绝对长度与比值，不能让身高和所有骨段长度同时独立控制 |
| 躯干体积 | 胸廓宽深、腹部前凸、腰侧丰满度、背部厚度 | 前后左右分别控制；胸廓骨架尺寸与胸部软组织体积不同 |
| 肢体体积 | 上臂、前臂、大腿、小腿的围度趋势 | 关节附近需要平滑过渡与受限变形，避免肘膝变成突然缩小的连接器 |
| 局部体表 | 肩部圆润度、臀部体积、肌肉轮廓清晰度 | 第一版属于艺术形状参数，不标为测量所得肌肉质量或体脂率 |
| 手足与头 | 手掌宽长、足长宽、头部宽高 | 会改变抓握点、脚底支撑和头发包络，宜放到第二阶段 |

首轮建议仅开放十个方向：身高、腿身比、肩宽、骨盆宽、胸廓深度、腰腹丰满度、上臂围度、大腿围度、头宽和下颌宽。按依赖逐步接通，不要求同时开放全部 UI。范围先取参考附近的小邻域；具体上下限经形体与动作验收后登记，不能用一个未经验证的统一 ±30% 范围覆盖全身。

采用控制优先级：先确定原型和总身高，再分配身体比例，再调软组织，最后调局部特征。用户锁定的尺寸作为硬条件；其余参数允许求解器调整。求解失败应返回无法同时满足的条件，不能静默截断后假装原意已实现。

### 4.2 “胖瘦”和“肌肉”应拆开

建议保留全局趋势与局部分布两级。全局丰满度只提供一个初始变化方向，腹部、腰侧、臀腿、脸颊可以偏离该方向。肌肉轮廓与丰满度可同时变化，才能表示厚实、瘦削、肌肉明显但腹部丰满等组合。

现有力量模型继续作为独立能力配置。将来若有依据，可以由体格给力量设置一个建议先验，但训练水平和实际能力不能仅由可见肌肉大小决定。由外形估算体积也不能直接得到可信质量；现有表面尚无完整闭合流形验收，自动体积积分不应先被当作可靠依据。

### 4.3 同一参考不应承担无限外推

当前参考附近的成人变化可以作为首个原型族。更大年龄跨度、显著不同身体结构或强风格化比例，应允许新增有来源的原型和适用域，共享关节语义与接口。新增原型可以保存自己的函数、参数、关系和来源，不必提交预制网格。

不同原型之间只有在曲面语义对应、关节和接口一致时才允许混合；否则采用离散选择。尤其不把儿童简单实现为成年人的全局缩小，也不把改动 `BODY_SEX` 字符串当作新增一类人体的完成标准。

## 五、符合现有函数资产约束的形变实现

### 5.1 增加空间变形层

设参考曲面为 `S0(u,v)`，个人参数为 `p`。建议建立在人体参考空间中定义的变形函数 `W(x,p)`，使个人中立表面成为 `Sp(u,v)=W(S0(u,v),p)`。变形控制量来自骨架锚点和局部坐标，位移场采用平滑、有局部支持的基函数。此处是针对项目的设计建议，未实现或验证。

粗层改变比例，次层改变软组织分布，细层处理鼻唇、眼睑、肌肉与关节修正。粗层可采用局部 FFD 控制格或解析轴向缩放场；最终选择应通过小范围原型比较确定。[4] 优先保留可读的控制点、基函数系数和语义作用域，避免保存每个显示顶点的一整套变形目标。

`p=0` 设置明确的基准恢复路径，直接走当前 R2 求值流程。源系数包保持可追溯，个人变化记录在派生配方中。基准恢复属于待验证目标，不能仅因公式写了零位移就宣称重建逐位一致。

### 5.2 全部曲面必须共享变形语义

身体、左腿、细节、五官和连接带不能各用一套互不协调的尺度。相同参考点通过同一个 `W` 得到相同目标点；接口两侧有厚度或间距的点仍是两个点，不应为了避免裂缝强行焊接。

优先在曲面求值层接入变形，使内部点、边界曲线、径向小腿图表及共享细分误差探针都看到新形体。若只在采样完成后移动顶点，原采样误差指标不再自动适用于变形后的曲面。新增层必须把误差评估放在最终曲面上，或另给经过验证的误差传播界限。

几何法线从变形后的切向导数重建；对于可微且非奇异的空间变形，可用 `normalize(J_W^-T n)` 转换原法线。原来的拟合法线场和细节法线也要统一坐标处理，不能只更新位置，留下旧法线造成假凹凸。分片基函数边界必须处理导数连续性或明确采用单侧规则。

共享位置、共享绑定根、共享编码继续服从 R10 的生成顺序。新增 `landmarkId` 和 `surfaceDomainId + (u,v)` 作为可跨采样精度使用的语义地址；不要依赖一次自适应细分生成的数字顶点 ID 在不同精度下不变。

### 5.3 个人骨架与新中立绑定

用相同的比例参数生成个人关节位置，但不要求所有关节机械地跟随软组织位移。骨架宽度影响关节；腹部丰满度通常主要影响表面。建议骨架形变与体表形变共享上游参数、各自使用合适的规则。

每次创建个人形体，生成个人中立骨架、骨段长度、局部轴、inverse bind、蒙皮权重和支撑点，然后在动作阶段保持该个人骨长不变。这同时满足“不同人比例不同”和“单个人动作中骨头不伸缩”。DQS 继续作用于新的中立形体，缩放不进入当前纯旋转平移的调色板。[5]

权重可以继承参考语义作为初值，但是否可以完整复用必须由形体域决定。明显改变肩盆和肢体比例时重新求解绑定更稳妥。R10 中 60 mm 扩散带等固定长度是现有算法参数，变形范围扩大后应审查其相对尺度；不能默认适用于任意身高。

### 5.4 动作与接触同步变化

`motion/vendor/rig.mjs` 的 `rigFromSource(document)` 已从传入节点计算肢体长度，这给个人化适配提供入口。上层 `NaturalLocomotion`、`MotionLabPose` 仍固定读取 `R2_RIG`，需要通过实例持有的 `resolvedRig` 接入。保留来源锁定的 vendor 核心，先在适配层完成变化；接口可传入个人节点不代表整个动作核已适配所有比例。

必须同步更新：脚底高度和支撑采样、手掌接触偏移、手臂可达性、躯干碰撞包络、导航半径、坐卧接触及持物间距。源动作可以贡献旋转和时序，但它在不同身材上的手脚落点不能照搬。身高增加不意味着把世界中的地面、桌子或持物目标一起放大。

现有 0.1 mm 骨长误差阈值和 12 mm 手脚目标误差是代码里的约束；个人化之后首先切换它们比较的参考对象，不能通过放宽阈值使错误姿态通过。若新范围需要不同阈值，另行说明用途和证据。

### 5.5 身材与姿态的组合修正

肩腋、肘膝、腹部和髋部需要 `correction(shape, pose)`，不能期待中立形体正确就保证弯曲后自然。可逐步增加少量局部解析修正：肘内侧压缩、上臂外侧体积修正、髋屈时腹股沟过渡、肩抬起时腋窝过渡。参数记录适用体型和姿态区间。

这些先属于艺术修正模型。SMPL 的身份与姿态分层提供方法参考，但本项目没有对应训练数据，不能把自编函数称为经过学习或实测的肌肉、皮肤动力学。[1] 第一阶段不宜承担全身软组织仿真。

## 六、外貌重塑的优先级

### 6.1 先轮廓与五官关系，再皮肤细节

建议按全身剪影、头部轮廓、五官布局、表面外观、微细节五层推进。角色在较远处主要靠比例和发型被区分，近处再依靠五官和皮肤；这是本项目的制作优先级建议，不是对现有画面的评价。

面部第一批可考虑：脸宽与脸长、下颌宽度与下巴前后、颧部宽度、眼距、鼻梁突出度、鼻翼宽、嘴宽、唇厚和耳部突出度。先完成八个左右有明确依赖的控制，再扩大数量。鼻、唇、眼睑和口腔是体积与边界问题，不能只靠噪声或颜色变化替代。

眼球中心、眼睑边界、嘴角、鼻底、下颌与头颈接口是关键锚点。眼距变化需要协调眼眶和眼球位置；眼睑还需保持合理闭合关系。脸宽变化需要影响耳位、颧部和下颌，但不应把牙齿、舌头等内容无差别缩放。先核查当前曲面域是否支持这些控制，未覆盖的结构应明确标为不支持。

脸型身份参数长期保存，表情值留在运行状态。表情控制再组合眨眼、视线、口型等通道，并处理冲突。FLAME 与 MetaHuman 的分层可作为组织参考；本项目并未因此自动拥有其表情解剖和绑定能力。[2][3]

### 6.2 程序化材料

第一步接通皮肤基色、粗糙度、局部色差、唇色、虹膜色与头发颜色。颜色用明确的线性或显示色空间约定保存，避免不同板块把同一数值解释成不同颜色。可见皮肤颜色可作为艺术参数，暂不把一个 RGB 值等同于已标定的黑色素含量。

雀斑、痣、斑点等稳定特征采用人物种子和中立表面坐标生成；出汗、湿润等属于状态叠加。不要用世界坐标噪声驱动永久皮肤特征，否则角色移动或重新采样时容易产生特征漂移。需要位置可编辑的特征保存语义域坐标、半径和强度，不保存贴图。

年龄外观可以联动皱纹、皮肤表现、发量和少量轮廓变化，但作为显式外观配方。它不自动改变认知能力、性格或力量。逐步构建不同年龄原型的依据，比一个“年龄”滑块同时暗改所有系统更容易维护。

### 6.3 毛发与衣物

现有毛发已使用曲面域求发根，这是可保留的基础。扩展时把发际线、密度、长度、卷曲、束流方向、直径和颜色分开。头型改变后，重新求发根和方向，并更新头皮包络；当前固定半径场需要变换或从个人头部重新派生。

毛发随机域按身体、脸、头发、皮肤分别划分。更换发型不应改变身高或五官。减少毛发数量时，可用发根稳定键的确定性筛选保持子集一致，避免观察精度变化导致发型身份重抽样。

衣物和饰品目前只有定义引用，预览器尚未安装任意部件。未来衣物同样采用函数配方、尺寸、松量和附着约束生成，先做一类简单衣物的适配；身体字段就绪不代表自动获得任意衣服不穿模能力。

## 七、性格、行为与身体如何协同

### 7.1 用可解释的偏好参数起步

第一版性格建议使用游戏设计参数，例如社交主动性、谨慎程度、耐心、探索偏好、任务坚持程度和表达强度。这些参数不承担心理测量意义。职业角色、长期目标、当前需求、关系记忆分别保存，避免一个“性格标签”承担全部行为逻辑。

同一任务的候选评分可以采用：需求收益、个人偏好、角色职责、关系因素，减去时间、疲劳和失败代价。各项先归一到清楚的区间，再用版本化权重组合；权重记录为设计配置。不可执行的任务先由能力与环境硬条件排除，不能因为评分高就越过可达性和接触预检。

现有日常调度已经有需求、冷却和疲劳恢复，可在其候选排序阶段加入个人权重，并保留失败封锁和工具归还闭环。先让两个 NPC 在相同世界下有可解释的不同选择，再考虑更复杂的规划系统。

### 7.2 表达风格通过受限通道进入动作

性格可以请求不同停顿长度、视线停留、手势幅度和可接受步速；动作层负责限幅和接触约束。任何手势叠加都必须由明确的动作混合层处理，不能直接覆盖已经负责持物或落脚的关节。

当前 `NaturalLocomotion` 用 `tempo` 调节动作推进，后续应明确它与身体时钟、疲劳和任务时间的关系。不要通过整体加速生理时钟来表现“性格急躁”。语言模型若参与，只输出允许的任务意图和表达请求，身体参数和瞬时姿态仍经过同一校验入口。

| 人物组合示例 | 外貌 | 性格与选择 | 执行约束 |
| --- | --- | --- | --- |
| A | 高瘦、长脸、短发 | 谨慎，倾向确认可执行条件后行动 | 臂长改变可达范围，力量由能力配置决定 |
| B | 与 A 相同外貌 | 社交主动，偏好交互与问候 | 保留与 A 相同身体能力，不因性格扩大关节范围 |
| C | 较矮、宽肩、圆脸 | 与 A 相同性格 | 使用个人步态适配和接触点 |
| D | 与 C 相同定义 | 疲劳较高、当前情绪低落 | 运行状态改变休息倾向，导出角色模板时不把疲劳固化 |

上述是可控组合的验收案例，不是外貌与性格的自然对应关系。

## 八、让随机生成具有质量和可重复性

建议采用“原型 → 有关联的体格参数 → 局部差异 → 外观配方 → 独立性格 → 约束检查”的流程。不要把每个滑块独立均匀随机到上下限。第一版可以使用人工设计的几组参数相关规则，但必须标为艺术采样分布，不能称为真实人口统计。

每个随机域采用由主种子、域名和版本派生的子种子。PRNG 算法、键的规范化和派生方法固定版本；避免依赖遍历顺序，也避免使用运行时间。锁定一部分参数后，重新采样只影响未锁定域。

非法组合采用有限重试，超过预算返回失败或退回明确预设。若采用投影修正，应导出请求值、实际值和调整原因，让角色可以被精确重建。自动生成的定义要保存已解析参数与生成版本，种子用于再次派生，不是长期保存身份的唯一信息。

区分三个键：`definitionId` 表示角色配方，`instanceId` 表示世界中的一次实例，`geometryKey` 表示可复用的形体结果。几何键至少包含来源版本、规范化后的形体与脸部参数、生成器及绑定版本；若对应某档实际缓存，还要包含采样质量和误差策略。材料、毛发另有资源键，性格不进入皮肤几何键。

跨设备承诺应分层：人物参数和来源可精确一致；浮点求值及 GPU 输出先按约定误差比较，不能未经验证承诺逐像素一致。个人身份不能随相机变化；不同精度只改变展开细节，这也符合锁定的 Object DNA 原则。[7]

## 九、多个板块共同推进的接口

建议由共享契约规定输入输出，各板块维护自己的实现。所有板块可以先围绕接口设计和文件校验推进，但涉及真实动作与外观的结论保持 Candidate。

| 板块 | 主要输入 | 主要输出 | 文件落点建议 |
| --- | --- | --- | --- |
| 共享定义与来源 | 原型、参数、版本、用户锁定项 | 规范化定义、约束结果、来源记录 | 扩展 `CharacterPresets.js`、`NPCDefinitions.js`、`HumanDNAContract.json` |
| 身体形变 | 已解析比例与体积参数 | 曲面求值、个人骨架、尺寸查询 | 新增小型形变模块，接入 `surface-kernel.mjs`、`assembly.mjs`、`ReconstructionRig.js` |
| 面部身份 | 脸型参数、头部锚点 | 面部曲面变化、眼口耳锚点 | 独立面部函数模块，与身体共享头颈接口 |
| 皮肤毛发 | 外观参数、中立曲面坐标、头部锚点 | 材料参数、发根与曲线 | `CompactWorkbench.js`、`hair.mjs`、`CompactHairRenderer.js` |
| 绑定动作 | 个人骨架、曲面、任务接触目标 | 绑定数据、可达性、候选姿态 | `binding.mjs`、`MotionLabPose.js`、`NaturalLocomotion.js`；先保留 vendor 来源锁 |
| 性格日常 | 偏好、需求、角色职责、世界状态 | 可解释候选排序和任务意图 | `NPCDefinitions.js`、`NPCRoutineController.js`、既有任务入口 |
| 多人物实例 | 定义 ID、生成资源、实例状态 | 独立生命周期与调度 | 后续从全局 `HumanLab` 和页面身份逐步抽离 |

需要共同冻结的最小接口是：坐标与单位、关节语义 ID、头颈与肢体接口、参数所有者、实例骨架对象、资源版本，以及能力查询结果。不要把共享全局 `R2_RIG` 改成“当前 NPC 的骨架”；那会导致一个角色变化污染其他角色。参考数据只读，每个人持有自己的派生结果。

建议的查询职责包括 `resolveShape(definition)`、`evaluateSurface(domain,u,v,resolvedShape)`、`resolveRig(resolvedShape)`、`measureBody(query)` 和 `queryCapability(action,context)`。这些名称仅用于设计讨论，当前代码没有这些 API。查询不得推进时间或修改状态。

字段迁移应显式：旧 `character_preset@3` 导入时映射到零形变和原有能力，未知版本拒绝或进入明确迁移器。只有形变、骨架、绑定、运动、导出共同接通后，才能把 `arbitraryStature` 或 `compositionDrivesGeometry` 等能力标记改为可用。一个字段被解析，不等于能力完成。

人物切换采用事务：构建新定义与个人骨架 → 准备曲面、绑定、毛发和动作适配器 → 完成相应检查 → 一次替换引用 → 释放旧资源。沿用 R11 的忙闲前置条件，并扩大暂存所有权到整个角色；仅表皮暂存成功不足以保证身体与动作不会短暂处于两个版本。

## 十、性能与按需精度

R13 文档记录过身体生成进度处触发总时限的问题，并说明当前启动耗时尚未测量。因此不能让每一次滑块输入都启动完整高精度曲面、绑定和毛发生成，也不能承诺增加参数后性能不受影响。

建议分三条更新路径：纯材料参数直接更新材质；比例预览使用临时低成本表示；确认形体后再完整生成个人曲面、绑定和毛发。编辑器预览可以是内存中的粗采样或控制包络，不必保存网格资产。每个任务有版本号和取消机制，只有最新有效结果允许提交。

人物数量增加时，共享只读来源函数与编译代码，按形体键复用可共享结果；姿态、疲劳、接触和任务归各实例所有。远处人物减少几何细节、毛发密度和更新频率，交互中的手脚接触精度则按任务保持。精度需要同时考虑距离与交互用途，不能仅按相机距离决定。

未来应测量首次生成、换肤、改体型、改发型的耗时分布，Worker 峰值内存、提交时新旧资源并存内存，以及 1/10/50 人场景的实际代价。这些数字是待测项目，不是当前容量承诺。文档未把角色定义能力等同于多人运行能力。

## 十一、分阶段实施与完成条件

| 阶段 | 具体工作 | 文件层完成条件 | 后续运行验收目标 |
| --- | --- | --- | --- |
| P0：契约与实例参考 | 定义 shape 扩展、派生骨架和迁移；清点固定 R2 依赖 | 旧配方迁移规则、依赖表、参数单位和版本齐全 | 零形变恢复参考，实例之间互不污染 |
| P1：一个完整纵向案例 | 先接通受限身高变化，再加入肩宽或腿身比 | 曲面、骨架、绑定、脚底、运动和导出都消费同一结果 | 改身高后站立、走停、坐起、持物仍遵守接触 |
| P2：受限体型空间 | 接通首批约十个形体方向与组合约束 | 参数有作用域、边界和冲突报告，无虚假能力开关 | 参数端点、组合与动作下不产生明显裂缝或穿插 |
| P3：身份外貌 | 面部基础控制、皮肤和发型参数 | 锚点、随机域、材料坐标与导出一致 | 能区分角色；换发型不改脸，换精度不改身份 |
| P4：性格表达 | 偏好评分与受限表达请求 | 不绕过任务入口、能力预检和时间语义 | 相同世界下有可解释的不同选择，并能完成任务 |
| P5：多实例与预算 | 抽离全局状态，增加资源复用和精度策略 | 所有状态有实例所有者，资源释放边界清楚 | 多人同时运行的性能、接触、取消与恢复实测 |

P0 可以与性格字段设计、面部锚点设计分别推进；P1 是体型与动作两侧必须共同完成的整链案例。不要先堆积大量滑块，等到最后才发现骨长、手掌和脚底仍读取全局参考。

首个里程碑建议定为：同一来源可以保存并重建三份身高不同的个人定义，保持个人骨长固定，动作仍由现有单一提交入口负责。三种身高的具体范围待形变域确定。此目标很小，但能够暴露生成链里真正的耦合问题；它完成后，新增局部参数才有可复用通道。

## 十二、验证边界与待解决问题

文件层可检查参数 schema、来源哈希、模块依赖、版本迁移定义、全局参考残留、同一形体对象的传递、共享边界处理顺序、CPU/GPU 属性约定和事务提交路径。这些工作遵守当前“只验证文件内容”的要求。

几何求值、测量残差、变形场雅可比、碰撞、接触、动作回放、性能和视觉均属于另外的执行层，本轮没有进行。未来若开展运行验收，应覆盖中立值、单参数两端、容易冲突的参数对和有限随机样本，并把形体与动作交叉组合。

`det(J_W)>0` 可作为局部翻折检查的一部分，但有限采样不证明全局单射，也不证明表面无自交。接缝位置一致不证明切线光顺，蒙皮权重归一化不证明关节自然；文件检查不能将这些目标升级为已实现效果。

优先动作案例为：站立、走停、转向、坐起、抬臂、屈肘与双手持物。重点部位为肩腋、腹股沟、手腕、膝后、颈部与眼睑。保留“数值检查通过”“运行完成”“视觉接受”三个独立状态，继续沿用 Candidate、`runtimeVerified=false`、`visualAcceptance=false` 和 `productionReady=false`，直到各自获得证据。

尚待决定的产品项包括：美术风格的夸张范围、主要年龄与身体原型、近景面部的重要程度，以及目标设备与同时可见人数。这些会影响参数域、脸部复杂度和预算，但不妨碍先建立个人定义、曲面和骨架同步的基础。
